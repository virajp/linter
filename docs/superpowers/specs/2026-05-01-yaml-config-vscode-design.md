# Design: YAML Config + VS Code Extension Support

## Goal

Enable `@askviraj/linter-cli` to be used as a **shared ESLint configuration
package** in target repositories, with support for:

1. A **declarative YAML config** (`.config/linter.yaml`) for per-repo
   customizations.
2. A **VS Code-compatible auto-config** (`@askviraj/linter-cli/auto`) that the
   `dbaeumer.vscode-eslint` extension can load.
3. A **refactored CLI** that uses ESLint's programmatic API instead of spawning
   a subprocess, with curated argument handling.

## Background

Currently, `@askviraj/linter-cli` only works as a standalone CLI. It spawns
ESLint with `--no-config-lookup --config <bundled>` and blindly forwards all
user args. This means:

- Target repos cannot customize the bundled config.
- The VS Code ESLint extension cannot discover or load the bundled config.
- User args like `--config` can conflict with the CLI's internal config
  management.

This design introduces a **factory-based config builder** and a **YAML layer**
so that both the CLI and the VS Code extension share the same configuration
source.

## Architecture

### Package Exports

```json
{
  "exports": {
    ".": "./dist/index.js",
    "./auto": "./dist/auto.js"
  }
}
```

| Export                      | File            | Purpose                        |
| --------------------------- | --------------- | ------------------------------ |
| `@askviraj/linter-cli`      | `dist/index.js` | CLI launcher                   |
| `@askviraj/linter-cli/auto` | `dist/auto.js`  | Auto-config loader for VS Code |

### Config Resolution Flow

Both the CLI and VS Code use the **same resolution path**:

1. Look for `.config/linter.yaml` relative to `process.cwd()` (walking up to
   filesystem root, stopping at the first match).
2. If found, parse it and call `createConfig(parsed)`.
3. If not found, return the **bundled base config** unchanged.

```text
Target Repo
├── .config/
│   └── linter.yaml          ← User's declarative customizations
├── .vscode/
│   └── settings.json        ← Auto-generated / updated by --init
├── eslint.config.mjs        ← Auto-generated by --init
│   # export { default } from "@askviraj/linter-cli/auto";
├── node_modules/
│   └── @askviraj/linter-cli/
│       ├── dist/
│       │   ├── index.js     ← CLI
│       │   ├── auto.js      ← Auto-config loader
│       │   └── eslint.config.js  ← Bundled base config
│       └── package.json
```

## YAML Schema (`.config/linter.yaml`)

The YAML file is purely declarative. The parser converts it into options passed
to `createConfig()`.

```yaml
# Additional ignore patterns (merged before the base config)
ignores:
  - "**/generated/**"
  - "**/*.d.ts"

# Override rules per file-type config block defined in the base config.
# Supported keys: javascript, typescript, astro, json, jsonc, markdown,
#                 yaml, toml, html, css
overrides:
  typescript:
    rules:
      "@typescript-eslint/no-explicit-any": "error"
  css:
    rules:
      "css/no-invalid-at-rules": "off"

# Append arbitrary ESLint flat-config objects after the base config.
# Useful for project-specific plugins or rule sets.
configs:
  - name: "custom"
    files:
      - "**/*.ts"
    rules:
      "my-custom-rule": "error"
```

### Schema Rules

- `ignores` → optional `string[]`. Passed to `globalIgnores()` and prepended.
- `overrides` → optional object keyed by config name. Each value is merged into
  the matching base config's `rules` object via shallow merge.
- `configs` → optional `Linter.Config[]`. Appended verbatim after the base
  config.
- Unknown top-level keys are ignored with a warning.

## Factory Function (`createConfig`)

```ts
import type { Linter } from "eslint";
import { globalIgnores } from "eslint/config";
import baseConfig from "./eslint.config.js";

export interface LinterYamlOptions {
  ignores?: string[];
  overrides?: Record<string, { rules?: Linter.RulesRecord; }>;
  configs?: Linter.Config[];
}

export function createConfig(options: LinterYamlOptions = {}): Linter.Config[] {
  const configs: Linter.Config[] = [];

  if (options.ignores && options.ignores.length > 0) {
    configs.push(globalIgnores(options.ignores));
  }

  for (const base of baseConfig) {
    const clone: Linter.Config = { ...base };
    if (base.name && options.overrides?.[base.name]) {
      clone.rules = { ...base.rules, ...options.overrides[base.name].rules };
    }
    configs.push(clone);
  }

  if (options.configs) {
    configs.push(...options.configs);
  }

  return configs;
}
```

The factory is imported by both `dist/auto.js` and `dist/index.js` so CLI and VS
Code use identical config construction.

## `--init` Command

Running `npx @askviraj/linter-cli --init` scaffolds the target repo for VS Code
and CLI usage.

### Generated / Modified Files

#### 1. `eslint.config.mjs` (project root)

Created if it does not exist. If it already exists and `--force` is not passed,
`--init` prints a warning and exits `1`.

```js
// Auto-generated by @askviraj/linter-cli
// Run `npx @askviraj/linter-cli --init` to regenerate.
export { default } from "@askviraj/linter-cli/auto";
```

`.mjs` is used instead of `.js` to guarantee ESM regardless of the target repo's
`package.json#type`. The VS Code ESLint extension discovers `.mjs` config files
automatically.

#### 2. `.config/linter.yaml`

Created if it does not exist.

```yaml
# @askviraj/linter-cli configuration
#
# Add custom ignores, rule overrides, and additional config blocks below.

# ignores:
#   - "**/generated/**"
#   - "**/*.d.ts"
#
# overrides:
#   typescript:
#     rules:
#       "@typescript-eslint/no-explicit-any": "error"
#
# configs:
#   - name: "custom"
#     files: ["**/*.ts"]
#     rules: {}
```

#### 3. `.vscode/settings.json`

Created if `.vscode/` does not exist. Merged with existing settings if the file
already exists.

```json
{
  "eslint.useFlatConfig": true
}
```

Only the `eslint.useFlatConfig` key is added/updated. All other existing
settings are preserved.

### `--init` Flags

| Flag             | Behavior                                                                                                                                                                                         |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `--init`         | Scaffold `eslint.config.mjs`, `.config/linter.yaml`, and `.vscode/settings.json`. Fails if `eslint.config.mjs` or `.config/linter.yaml` already exist. `.vscode/settings.json` is always merged. |
| `--init --force` | Overwrite `eslint.config.mjs` and `.config/linter.yaml` if they exist. `.vscode/settings.json` is still merged.                                                                                  |

### Post-Init Workflow

After `--init`, the user edits `.config/linter.yaml` to customize rules. Both
the CLI and VS Code extension pick up those changes through the same `auto`
loader.

## CLI Refactor

### Argument Parsing

The CLI no longer blindly forwards all arguments to ESLint. It explicitly parses
a curated set of flags.

| Flag                      | Type       | Description                                             |
| ------------------------- | ---------- | ------------------------------------------------------- |
| `--init`                  | boolean    | Scaffold config files                                   |
| `--force`                 | boolean    | Allow overwriting existing files (paired with `--init`) |
| `--fix`                   | boolean    | Automatically fix problems                              |
| `--cache`                 | boolean    | Only check changed files                                |
| `--cache-location <path>` | string     | Path to the cache file or directory                     |
| `--quiet`                 | boolean    | Report errors only                                      |
| `--version`, `-v`         | boolean    | Show version                                            |
| positional args           | `string[]` | Files or directories to lint (default: `["."]` )        |

Unknown flags produce an error message and exit `1`.

### Execution Flow

```text
parseArgs(rawArgs)
│
├─> --init         → scaffold files → exit 0
├─> --version      → print version  → exit 0
│
└─> lint mode
    │
    ├─> find .config/linter.yaml (walk up from cwd)
    ├─> build config: createConfig(parsedYaml || {})
    │
    ├─> const eslint = new ESLint({
    │       overrideConfigFile: true,
    │       overrideConfig: config,
    │       fix: args.fix,
    │       cache: args.cache,
    │       cacheLocation: args.cacheLocation,
    │       quiet: args.quiet,
    │     })
    │
    ├─> const results = await eslint.lintFiles(targets)
    ├─> if (args.fix) await ESLint.outputFixes(results)
    ├─> const formatter = await eslint.loadFormatter()
    ├─> const output = await formatter.format(results)
    ├─> if (output) console.log(output)
    └─> process.exit(errorCount > 0 ? 1 : 0)
```

### Why Programmatic API?

- Gives full control over config injection (`overrideConfig`).
- Eliminates subprocess spawning overhead.
- Prevents user arguments from interfering with internal config management.
- Allows graceful error messages for YAML parse failures or missing files.

## VS Code Extension Integration

### Discovery

The VS Code ESLint extension automatically finds `eslint.config.mjs` (and other
`eslint.config.*` variants) in the workspace root. Once found, it loads the
module, which imports `@askviraj/linter-cli/auto`. The `auto` module reads
`.config/linter.yaml` and exports the built config array.

### Required Settings

`.vscode/settings.json` gets `eslint.useFlatConfig: true` via `--init`. This
ensures the extension uses flat-config mode even on older versions.

### Config Reloading

The extension watches `eslint.config.mjs` for changes. **It does not watch
`.config/linter.yaml`.** After editing `.config/linter.yaml`, the user must run
**"ESLint: Restart ESLint Server"** from the VS Code command palette (or touch
`eslint.config.mjs`). This is a documented limitation.

## Error Handling

| Scenario                             | Behavior                                                                   |
| ------------------------------------ | -------------------------------------------------------------------------- |
| `.config/linter.yaml` missing        | Silently fall back to bundled base config                                  |
| `.config/linter.yaml` malformed YAML | Print a clear parse error to `stderr`, exit `1`                            |
| `.config/linter.yaml` unknown keys   | Warn to `stderr`, ignore unknown keys, continue                            |
| `--init` and files exist             | Print which files exist, suggest `--force`, exit `1`                       |
| No files to lint                     | Return exit `0` (existing behavior via `--pass-on-no-patterns` equivalent) |
| ESLint throws during lint            | Print error, exit `1`                                                      |

---

## Backward Compatibility

- Existing CLI usage (`npx @askviraj/linter-cli`) continues to work.
- Without `--init`, behavior is unchanged: the bundled config is used.
- `--version` / `-v` behavior is unchanged.
